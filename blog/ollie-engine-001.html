Dev Log · OllieEngine

OllieEngine #001

1 October 2026 / 3 min read / Oliver Creese

A brand new project: my own game engine, built from scratch in C++. No Unreal, no Unity, just me, OpenGL and a lot of matrices. Oh boy.

Why Build an Engine?

I've spent a long time building games on top of Unreal and Unity, and I wanted to properly understand what's happening underneath them. OllieEngine is my way of doing that. Every system in it is something I've had to think through and write myself, from opening a window all the way to getting a 3D cube on screen that you can fly around.

The Foundations

The engine sits on top of a few small libraries: GLFW for the window and input, GLEW to load OpenGL 3.3 core functions, and GLM for vector and matrix maths, all built with CMake. The engine itself is a library, and the game is a separate executable that plugs into it through an Application interface with Init, Update and Destroy. The Engine runs the main loop: it polls input, works out delta time, updates the game, then draws the frame.

Rendering

Meshes wrap up the vertex and index buffers and are described by a data-driven vertex layout, so the same code can handle different vertex formats. Materials bind a shader program and its parameters. Instead of drawing straight away, anything that wants to be drawn submits a command to a render queue, and the engine draws the whole queue once per frame using the main camera's view and projection matrices. I also added proper shader compile and link error checking, so a broken shader now tells me what's wrong instead of just failing silently.

Scene, GameObjects and Components

The scene holds a hierarchy of GameObjects, each with a position, rotation and scale. A child's world transform is built by combining its own transform with its parent's, all the way up the chain. Behaviour lives in components, and each component type gets its own ID from a small templated counter, so the engine can look components up without relying on C++ RTTI. Right now there's a mesh component, a camera component and a player controller that gives a free-fly camera: hold left mouse to look around, WASD to move, and Q and E to go up and down. To test the hierarchy I've been playing with a spinning cube that has a smaller child cube orbiting around it.

Switching to Quaternions

Rotation started out as Euler angles, which is fine until things start combining in strange ways. I've switched everything over to quaternions. The camera yaws around the world's fixed up axis but pitches around its own right axis, which gives the familiar first-person feel where the camera can't tip over. The rotation also gets normalised after each change so small floating-point errors don't pile up over time.

Challenges

Some bugs hide really well. The index buffer was being sized using sizeof(float) instead of sizeof(uint32_t), and it only worked because both happen to be 4 bytes. The mouse look was also multiplying the mouse movement by delta time. The mouse movement is already the amount moved that frame, so this made the camera turn faster or slower depending on the frame rate. Removing it means the same swipe of the mouse always turns the camera by the same amount.

Current Issues

The camera builds its own view matrix without its own scale, but it still picks up the scale of any parent it's attached to, which would skew the view under a stretched parent. The mouse's previous position is also being updated in two places each frame, which can lose movement when several mouse events arrive in one frame. Finally, the render queue sets the model, view and projection matrices directly on the shader instead of going through the material, which I want to tidy up before the renderer grows any further.

The code is all on GitHub, and you can read more about the project on the OllieEngine project page.
